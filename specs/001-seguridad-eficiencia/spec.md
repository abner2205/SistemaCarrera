# Especificación: 001 - Auditoría y Remediación de Seguridad de Datos y Eficiencia de Ejecución

**Estado:** Aprobado
**Fecha:** 2026-11-13

## 1. Propósito y Contexto
- **Qué**: Diagnóstico verificable mediante una suite de pruebas automatizadas aisladas (bajo enfoque TDD: prueba que evidencia la falla, corrección en el sistema y validación en verde) junto con la remediación integral de seguridad de datos, integridad transaccional, reglas de negocio y eficiencia de ejecución en **SistemaCarrera**.
- **Por qué**: El análisis del sistema actual evidencia ausencia de pruebas automatizadas reales, endpoints locales expuestos sin autenticación ni validación de archivos o identificadores, condiciones de carrera entre móviles y PC con confirmaciones anticipadas falsas, pérdida o bloqueo de datos por ausencia de configuración WAL/FK/transacciones y borrados en cascada destructivos, falta de sanitización CSV y respaldos automáticos, inyección de datos ficticios en carreras vacías, acoplamiento del servidor/datos con diálogos de interfaz gráfica y cuellos de botella por recargas duplicadas e imágenes sin escalar. Resolver estos puntos garantiza confiabilidad, seguridad y fluidez operativa en competencias reales.

## 2. Requisitos Funcionales (EARS)

### Entorno de Pruebas Aislado, Desacoplamiento y Carga Operativa
- **RF-01**: El sistema DEBERÁ permitir configurar rutas aisladas de base de datos y almacenamiento para que la suite de pruebas automatizadas se ejecute sin leer ni alterar la base de datos `carrera.db` ni las carpetas `Storage/` de producción.
- **RF-02**: Las capas de servidor web y de gestión/persistencia de datos DEBERÁN operar y reportar errores sin depender de infraestructura de ventana gráfica ni cuadros de diálogo modales de escritorio, permitiendo su ejecución autónoma en pruebas sin interfaz visual.
- **RF-03**: CUANDO un usuario abra o cree una carrera vacía en operación real, el sistema DEBERÁ mantener la carrera limpia sin insertar automáticamente categorías, hits ni corredores ficticios de prueba.
- **RF-04**: CUANDO el sistema opere bajo la carga máxima objetivo (hasta 40 corredores por carrera, 3 hits activos simultáneos, 2 teléfonos de jueces conectados concurrentemente y picos de 10 llegadas por minuto), el sistema DEBERÁ procesar el 100% de las llegadas sin pérdida de datos, con cero errores de base de datos bloqueada (`database is locked`) y sin congelamientos visuales.

### Seguridad del Servidor Web Local (LAN, QR y Validación de Archivos)
- **RF-05**: CUANDO se inicie la aplicación de escritorio, el sistema DEBERÁ generar una única vez por sesión de arranque un token aleatorio URL-safe de 12 a 16 caracteres (estable aunque el usuario cambie o recargue vistas) e incluirlo en la URL del código QR (`https://<IP>:5001/index.html?token=...`), mostrando además la URL completa y el token en pantalla como respaldo manual, manteniendo habilitados los puertos HTTP (5000) y HTTPS (5001).
- **RF-06**: MIENTRAS el servidor web esté activo, el sistema DEBERÁ permitir la carga sin token de los recursos estáticos necesarios para presentar la interfaz móvil y DEBERÁ exigir el token vigente de sesión (vía cabecera `X-Auth-Token` o parámetro de consulta `?token=`) en todos los endpoints operativos `/api/*`.
- **RF-07**: SI una petición dirigida a cualquier endpoint `/api/*` carece de token o presenta una credencial inválida, ENTONCES el sistema DEBERÁ rechazarla con estado HTTP `401 Unauthorized` sin modificar la cola pendiente, los archivos en disco ni la base de datos.
- **RF-08**: CUANDO el cliente web móvil reciba una respuesta HTTP `401 Unauthorized` en cualquier operación o sondeo, el sistema DEBERÁ notificar visualmente al juez en pantalla que la credencial es inválida o la sesión cambió y que debe reescanear el código QR o actualizar el token.
- **RF-09**: CUANDO un juez autorizado envíe una fotografía al endpoint de carga, el sistema DEBERÁ verificar que el archivo no esté vacío, respete el límite máximo de **10 MB** y corresponda a un formato permitido (**JPEG, PNG o WebP**) validado mediante firma binaria (*magic bytes*) y decodificabilidad real de imagen.
- **RF-10**: SI el archivo cargado está vacío, carece de identificador temporal válido, supera los **10 MB** o no es una imagen JPEG/PNG/WebP decodificable, ENTONCES el sistema DEBERÁ rechazar la solicitud con el estado HTTP adecuado (`400 Bad Request`, `413 Payload Too Large` o `415 Unsupported Media Type`) y un cuerpo JSON con error descriptivo sin escribir archivos en disco.
- **RF-11**: CUANDO un cliente móvil solicite asignar un dorsal o descartar una fotografía en `/api/*`, el sistema DEBERÁ validar el identificador `IdFoto` para impedir secuencias de recorrido de directorios (*path traversal*: `..`, `/`, `\`) o caracteres inválidos, rechazando con HTTP `400 Bad Request` cualquier valor malformado.

### Carrera Activa, Concurrencia, Atomicidad y Sincronización Móvil-PC
- **RF-12**: SI no existe una carrera activa seleccionada en la mesa de cronometraje al recibir una asignación remota, ENTONCES el sistema DEBERÁ rechazar la solicitud (sin seleccionar automáticamente ninguna carrera previa de la base de datos) informando explícitamente que no hay carrera activa en mesa.
- **RF-13**: CUANDO el operador seleccione o cambie la carrera activa en la mesa de escritorio, el sistema DEBERÁ limpiar la categoría activa de pizarra y limpiar la cola de fotografías pendientes tanto en la vista de escritorio como en la cola en memoria del servidor (eliminando sus archivos temporales huérfanos en `Fotos_Temp`), para evitar que la interfaz o los teléfonos sincronicen o asignen capturas de la carrera anterior a la nueva carrera.
- **RF-14**: CUANDO un juez móvil solicite asignar un dorsal a una fotografía pendiente, el sistema DEBERÁ completar las validaciones y la persistencia antes de responder al dispositivo móvil el resultado real (`200 OK` solo tras éxito real; `400`, `404`, `409` o `422` según corresponda a datos inválidos, captura inexistente, conflicto concurrente o rechazo de regla de negocio).
- **RF-15**: CUANDO el cliente web móvil envíe una solicitud de asignación o descarte, el sistema DEBERÁ deshabilitar temporalmente los controles de esa captura para prevenir envíos duplicados por doble clic y, ante respuestas de error del servidor distintas de `401`, mostrar el mensaje descriptivo sin marcar la captura como aceptada.
- **RF-16**: CUANDO dos o más solicitudes concurrentes intenten asignar o descartar la misma fotografía pendiente (entre múltiples dispositivos móviles o entre un móvil y la PC), el sistema DEBERÁ garantizar exclusividad mutua para que únicamente la primera operación válida procese la captura y las subsecuentes reciban rechazo por conflicto.
- **RF-17**: CUANDO se registre el tiempo de un corredor, el sistema DEBERÁ ejecutar de forma atómica el cálculo del tiempo neto usando la hora original de llegada capturada por el servidor al recibir la fotografía, el guardado en base de datos, la actualización de cierre del hit si corresponde, el traslado de la fotografía a almacenamiento definitivo y el retiro de la captura de la cola pendiente.
- **RF-18**: SI ocurre un error de validación o persistencia durante el registro de un tiempo, ENTONCES el sistema DEBERÁ revertir cualquier cambio parcial en base de datos y conservar íntegra la fotografía en su estado y cola pendientes para reintento o descarte.
- **RF-19**: SI la hora de llegada asociada a una fotografía es anterior a la `Hora_Inicio` del hit del corredor, ENTONCES el sistema DEBERÁ rechazar el registro informando que no se permiten tiempos netos negativos y mantener la captura en estado pendiente.
- **RF-20**: CUANDO se registre válidamente el tiempo de un corredor, el sistema DEBERÁ evaluar si restan corredores en estado `Activo` sin tiempo dentro de ese hit; cuando todos los corredores `Activo` del hit ya tengan tiempo (excluyendo `DNS`/`DNF` y existiendo al menos un corredor `Activo`), DEBERÁ establecer `Hora_Fin` garantizando que sea mayor o igual a la hora de llegada máxima registrada en dicho hit.

### Integridad de Catálogos, Reglas `DNS`/`DNF`, Borrados y SQLite
- **RF-21**: CUANDO el administrador gestione corredores, el sistema DEBERÁ permitir modificar su estado entre `Activo`, `DNS` y `DNF` únicamente mientras el corredor no tenga un tiempo registrado, y DEBERÁ prohibir cambiar el estado a `DNS`/`DNF` o cambiar el hit asignado de cualquier corredor que ya cuente con un tiempo registrado.
- **RF-22**: SI un operador intenta eliminar un corredor, hit, categoría o carrera que contenga al menos un corredor con tiempo registrado, ENTONCES el sistema DEBERÁ bloquear la eliminación e informar que el registro histórico está protegido (indicando el uso de estados `DNS`/`DNF` cuando corresponda).
- **RF-23**: CUANDO el operador cree o edite carreras, categorías, hits o corredores, el sistema DEBERÁ validar que la carrera tenga nombre no vacío y fecha válida, que los nombres de categorías y hits no estén vacíos ni duplicados dentro de la misma carrera, y que cada corredor tenga nombre no vacío y dorsal entero positivo (> 0) único en su carrera.
- **RF-24**: CUANDO el sistema genere nombres de carpetas o archivos definitivos a partir de nombres de carrera, categoría o corredor, el sistema DEBERÁ sanitizar secuencias de ruta (`..`, `.`, separadores y caracteres inválidos), prevenir colisiones de nombres de archivo y acotar la ruta completa dentro de límites seguros del sistema de archivos.
- **RF-25**: MIENTRAS la aplicación utilice la base de datos SQLite `carrera.db`, el sistema DEBERÁ configurar explícitamente el modo `WAL` (`PRAGMA journal_mode=WAL`), llaves foráneas activas (`PRAGMA foreign_keys=ON`) y tiempo de espera ante contención (`PRAGMA busy_timeout`), así como ejecutar de forma segura e idempotente la creación o actualización de esquema e índices requeridos sobre bases de datos previas.

### Sanitización CSV, Limpieza de Temporales y Respaldos
- **RF-26**: CUANDO el operador exporte corredores o resultados a CSV, el sistema DEBERÁ neutralizar anteponiendo un apóstrofe (`'`) todo campo de texto editable por el usuario que comience (directamente o tras espacios iniciales) con `=`, `+`, `-`, `@`, tabulador (`\t`) o retorno de carro (`\r`), manteniendo intactos los valores formateados de sistema como `--:--:--`.
- **RF-27**: CUANDO se inicie la aplicación de escritorio, el sistema DEBERÁ eliminar cualquier archivo de imagen huérfano en los formatos soportados (`.jpg`, `.jpeg`, `.png`, `.webp`) presente en `Fotos_Temp` que no pertenezca a capturas pendientes activas de la sesión actual, preservando `.gitkeep` y sin alterar jamás las fotografías definitivas en `Fotos_Definitivas`.
- **RF-28**: CUANDO se inicie la aplicación existiendo una base de datos `carrera.db` previa o antes de ejecutar actualizaciones de esquema/índices, el sistema DEBERÁ generar una copia de respaldo consistente de SQLite en una carpeta dedicada conservando como máximo **10 respaldos** históricos (rotando los más antiguos); si falla el respaldo, DEBERÁ registrar el error sin bloquear el arranque de la aplicación.

### Eficiencia de Ejecución, Memoria e Interfaz Reactiva
- **RF-29**: MIENTRAS se ejecuten tareas de inicialización/migración de base de datos, respaldo SQLite, generación de QR, decodificación de imágenes o exportación CSV, el sistema DEBERÁ procesar las operaciones de E/S y cómputo pesado fuera del hilo principal de interfaz para evitar congelamientos visuales.
- **RF-30**: CUANDO se registre un nuevo tiempo o cambie la categoría activa de la pizarra, el sistema DEBERÁ ejecutar una única recarga consolidada por evento en cronometraje y en la pizarra (eliminando recargas dobles), descartar resultados obsoletos o fuera de orden ante ráfagas concurrentes y reutilizar los logotipos en caché sin releerlos desde disco si sus rutas no han cambiado.
- **RF-31**: MIENTRAS la interfaz muestre fotografías de meta, miniaturas o logotipos, navegue entre vistas o sondee pendientes desde el cliente móvil, el sistema DEBERÁ decodificar imágenes a escala adecuada para visualización sin retener tamaños completos innecesarios, detener temporizadores y suscripciones al descargar vistas (evitando ventanas de pizarra huérfanas) y evitar que el sondeo móvil lance peticiones nuevas mientras una anterior siga en curso.

## 3. Casos Límite y Restricciones
- **Concurrencia y accesos simultáneos**:
  - Dos teléfonos o un teléfono y la PC intentan asignar o descartar la misma fotografía pendiente de forma simultánea.
  - Ráfagas de hasta 10 llegadas por minuto desde 2 dispositivos móviles mientras 3 hits activos actualizan sus cronómetros y la pizarra recalcula posiciones.
  - Cambios rápidos consecutivos de categoría en pizarra o llegada rápida de múltiples tiempos (garantizar que una consulta lenta anterior no sobrescriba resultados más recientes).
  - Solicitud remota recibida cuando `CarreraActiva` aún no se ha seleccionado en mesa o después de cambiar de carrera activa.
- **Valores fuera de rango y entradas maliciosas o inválidas**:
  - Peticiones a `/api/*` sin token, con token expirado de una sesión anterior o con token manipulado (`401`).
  - Carga de archivos de 0 bytes, mayores a 10 MB (`413`), archivos no imagen renombrados a `.jpg`, imágenes corruptas no decodificables (`415`) o `IdFoto` con `..`, `/`, `\` (`400`).
  - Dorsales <= 0, no numéricos o duplicados; nombres vacíos o duplicados de hits/categorías; nombres con caracteres especiales que excedan rutas o provoquen colisiones.
  - Campos CSV editables con prefijos peligrosos (`=1+1`, `  +cmd`, `-@SUM`, `\t=`, `\r+`) frente a valores válidos del sistema (`--:--:--`).
  - Intentos de eliminar carreras, categorías, hits o corredores con tiempos registrados, o cambiar a `DNS`/`DNF` o cambiar el hit de un corredor que ya cronometró.
  - Hora de captura anterior a `Hora_Inicio` del hit (tiempo neto negativo) o hit con solo corredores `DNS`/`DNF`.
- **Fallos de red, disco o base de datos**:
  - Microcortes Wi-Fi en el móvil durante el sondeo periódico (sin acumulación de solicitudes concurrentes y con aviso claro ante `401`).
  - Fallo de persistencia en `carrera.db` después de subir la fotografía (la foto temporal permanece en la cola y en `Fotos_Temp` para reintento sin pérdida de evidencia).
  - Fallo al crear el respaldo de `carrera.db` por permisos o disco lleno (se registra el fallo sin impedir que la aplicación arranque).
  - Ejecución de pruebas automatizadas sin ventana WPF y sin afectar `carrera.db` ni `Storage/` de producción.

## 4. Criterios de Aceptación
- [ ] **Aislamiento, desacoplamiento y TDD**: `dotnet test` ejecuta todas las pruebas de seguridad, integridad, concurrencia y rendimiento en verde sobre directorios y bases temporales aisladas, sin requerir ventana WPF en capas de servidor/datos, sin tocar `carrera.db` ni `Storage/` de producción y sin inyectar datos ficticios en carreras reales vacías.
- [ ] **Autenticación LAN y QR**: Al arrancar se genera un único token URL-safe de 12–16 caracteres estable entre cambios de vista, embebido en la URL del QR (`https://<IP>:5001/index.html?token=...`) y visible manualmente; HTTP (5000) y HTTPS (5001) permanecen activos; `wwwroot/` carga sin token; el 100% de `/api/*` sin token válido devuelven `401 Unauthorized`; y el cliente móvil muestra aviso visual ante `401`.
- [ ] **Validación estricta de carga e `IdFoto`**: El servidor rechaza con `400`, `413` o `415` y JSON descriptivo el 100% de archivos vacíos, > 10 MB, no-JPEG/PNG/WebP por *magic bytes* o no decodificables, así como el 100% de `IdFoto` con secuencias de *path traversal* (`400`).
- [ ] **Concurrencia, atomicidad y sincronización real**: Ante asignaciones remotas sin carrera activa responde rechazo explícito; el cambio de carrera limpia pizarra, cola pendiente en vista de escritorio y cola en memoria del servidor (eliminando sus temporales en `Fotos_Temp`); el móvil recibe `200 OK` solo tras persistencia real (o `400`/`404`/`409`/`422` en rechazo) con bloqueo anti doble clic; ante asignaciones/descartes simultáneos de una misma foto solo 1 prospera; ante fallo de guardado no se pierde la foto ni quedan registros parciales; se preservan tiempos originales y se rechazan tiempos netos negativos.
- [ ] **Reglas `DNS`/`DNF`, catálogos, borrados y SQLite**: Solo corredores sin tiempo pueden cambiar entre `Activo`/`DNS`/`DNF` o cambiar de Hit; el 100% de intentos de eliminar corredores, hits, categorías o carreras con tiempos registrados son bloqueados; nombres/dorsales duplicados o inválidos son rechazados; rutas definitivas están sanitizadas y acotadas; y `carrera.db` opera con `WAL`, `foreign_keys=ON`, `busy_timeout` y migración segura de índices/esquema.
- [ ] **CSV, limpieza de temporales y respaldos**: Toda exportación CSV antepone `'` a campos editables con prefijos peligrosos (aun con espacios iniciales) conservando intacto `--:--:--`; al arrancar se limpian archivos de imagen huérfanos (`.jpg`, `.jpeg`, `.png`, `.webp`) en `Fotos_Temp` preservando `.gitkeep` y `Fotos_Definitivas`; y se crean respaldos consistentes de `carrera.db` con retención máxima de 10 archivos sin bloquear el arranque ante fallos de copia.
- [ ] **Eficiencia bajo escala objetivo**: En simulación de 40 corredores, 3 hits activos simultáneos, 2 móviles concurrentes y picos de 10 llegadas/minuto se registran 0 errores `database is locked`, cada evento dispara máximo 1 recarga consolidada sin sobrescrituras fuera de orden, los logotipos se cachean, las imágenes se decodifican a escala eficiente, los recursos/temporizadores se liberan al navegar o cerrar, la UI no se bloquea por E/S y el sondeo móvil no solapa peticiones.
